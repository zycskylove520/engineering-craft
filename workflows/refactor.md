# 编排：重构（不改变外部行为）

1. **划定行为基线（G1 入口）**：先跑现有测试/检查，确认绿；记录基线输出，并把基线检查（命令 + 输出摘要 + 日期）落进 `.project_memory/tmp/VERIFY-LOG.md`——这就是重构的 G3 证据（重构走"基线绿"路径，不要求人为造红灯，见 `core/testing-strategy.md` §2）。**"行为不变"的判定依据（测试/基线输出）拿不到就不开工，先补测试或问清**（P0 第 9 条）。改前按 `core/memory/retrieval-and-writeback.md` §1 检索该模块的相关写法规范，重构后仍要符合既有约定。
2. **确定外部契约**：列清公开 API 与行为，重构中不得改变（契约见 `languages/` 与 `core/design-principles.md`）。
3. **识别坏味道**：重复代码、硬编码、职责错位、循环依赖、过深嵌套等，按影响面排优先级。
4. **小步安全重构**：每步只做一种变换（提炼函数/搬移/改名/消除重复），每步后跑基线检查保持绿；每步的检查结果追加进 VERIFY-LOG。
5. **测试护航**：行为不变靠测试担保；缺测试先补测试再重构（见 `core/testing-strategy.md`）。
6. **注释同步**：结构变化的声明注释同步更新（公开 API 契约尤其），函数体逻辑注释仍克制。
7. **验证**：全套检查 + 对比基线输出，确认行为无变化，结果落 VERIFY-LOG（见 `core/verification.md`）。G3 核验 VERIFY-LOG 有基线绿 + 全套证据才放行（P0 第 9/11 条）。
8. **写回记忆**：若形成新的架构/命名约定，更新工程记忆对应层并标日期。
9. **交付与追问**：说明行为未变的证据（基线对比输出）；涉及上线先走 `core/release-and-operate.md`，然后按 SKILL.md 第六节追问下一需求 + 是否需要调整，停下。
