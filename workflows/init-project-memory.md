# 编排：工程记忆主线（「开始工程」入口）

> 适用：用户发出「开始工程」→ 先经本编排进入工程记忆环节，再汇入需求循环。
> 覆盖**三种起点**：空项目 / 有代码无记忆 / 代码与记忆都在。前两种是建库，第三种是读库接续。
> 本文件只管"这次怎么建/怎么进"的**操作序列**；规格按需链接到 `core/memory/` 能力簇（见 `core/project-memory.md`）。细节不内联，避免新增能力时改本文件。

## 前置红线（与 SKILL.md §五常驻版一致，刻意重复）

1. **先确认项目根目录（强制前置询问，不得默认、不得跳过）**：读取当前会话目录作为默认候选，然后明确问用户一句：「是否在 `<候选目录>` 进行工程构建？若是请确认，或告诉我另一个项目根目录。」**这一问发生在下面任何目录状态判断之前**，不可被"直接建库/我先看代码"绕过（后者属 `SKILL.md` §4.1 红线第 2 条）。**用户确认前不得写任何文件**。原因：宿主 cwd 常与会话工作目录不同，凭默认直接开干会写错位置。用户给的路径与会话目录不一致时以用户确认为准；所有写入路径必须落在该已确认的项目根内，不越界。
2. **确定工程记忆目录**：默认 `<项目根>/.project_memory/`（隐藏目录）。标记是目录内的空文件 `.engineering-craft`（存在即表示"本 skill 创建/接管"）。**新建目录后第一步就写入该标记文件**——否则下次运行会把自建目录判成"存在但不带标记"。判据：目录存在且带标记 → 用；存在但不带标记（疑似别人的目录、名冲突）→ **绝不写入**，改用 `.project_memory_engineer/` 并同样打标记。

> 红线在 SKILL.md 常驻、此处按需重复，是**有意的防御性重复**：安全不能只靠按需加载的 workflow 保护。

## 起点路由（两段式：先确认根，再按目录状态分流）

**第一段（强制前置）**：即上面的红线 1——项目根未确认时只问"是否在此构建"、等确认，不做任何目录状态判断。

**第二段（根确认之后）按目录实际状态三分支**（这里的"是否询问"仅指是否再问"做什么/从哪步起"，不含根确认那一问）：

1. **目录已有项目代码（存在源码/项目文件），但还没有 `.project_memory/`** → **不再询问，直接建库**（走下面四步操作序列），建完再向用户汇报并问下一步。不拿"要不要建库/从哪步起"打断用户。
2. **目录是空的（无任何项目文件）** → 才问用户想做什么，再进入需求循环。
3. **目录已有 `.project_memory/`** → 才问用户是继续上轮、开新需求还是重建。

**误判防护**：判定"已有代码"看是否存在真实的源码/项目文件；**不要因为源码注释、README 里提到 ADR/PRD/流程字眼就误判成"走过流程"而停下来问用户**——注释不是交接物，只有落盘的 `.project_memory/` 与交接物文件才算。

## 四步操作序列

**步 1 · 通读（Read）**
按构建单元 / 顶层目录切批，**分批把整个项目源码读完，读不透不进下一步**。每批要挖的维度见 `core/memory/document-tree.md` §3 必挖清单（构建系统当架构读、目录职责逐个自悟、功能模块全链路、横切约定、例外反例）。大工程用多 agent 并行时按下方"多 agent 策略"，产出结构化模式候选落 `.project_memory/tmp/notes/`，不进规范层。

**步 2 · 规划（Plan）**
产出 `PLAN.md` 落 `.project_memory/tmp/`（临时产物，不进规范层）：逻辑文档树（每篇职责边界 + 为何单独成篇/为何合并）+ 覆盖映射表（源码顶层目录/模块类别 → 归属文档）。划分原则与两步定位测试见 `core/memory/document-tree.md` §1–3。**顶层 6 个标准职责目录固定全建（见规格）；"结构自定"指目录内按子系统/主题怎么分文件、分几篇——这部分由 agent 按证据自定，宁可多建、不混职责**；规划产物可给用户过目（结构可见、可审）。

**步 3 · 落盘（Write）**
按规划建树，逐条陈述按 `core/memory/content-model.md` 执行（五件套：稳定 id + kind + 陈述 + 证据 + 日期与事实等级；写规则不写清单；能套用的写成配方；每篇边界声明）。落盘后更新 INDEX。

**步 4 · 自检（Verify）**
按完整性清单核对，结论**附具体证据**（实际生成的文档清单 + 覆盖映射 diff），不能只写"已核对"：
- [ ] 6 个标准职责目录齐全（architecture/conventions/api-contracts/data-model/testing/build + 3 根文件 INDEX/status/open-questions），没有把不同职责堆进一个 modules 大杂烩；每个职责目录内按子系统分文件、数量动态；增补目录已在 INDEX 登记
- [ ] 每个一级子系统在规划中有归属，且有自己的规范单元（没有多个子系统挤进一个文件）
- [ ] 每个子系统有写法文档，且内容是 RULE 规则非清单；高频动作有配方式规则（抄哪个文件/改哪几处/怎么验证）
- [ ] 段落级一关注点：没有一段混多件事
- [ ] 构建系统按架构梳理（分层/耦合/边界，非配置罗列）
- [ ] 每条陈述五件套齐（id + kind + 陈述 + 证据 + 日期与事实等级）；清单式陈述 0 条（扫描计数词）；**证据主体是文件路径+模式描述、行号只在括号内辅助**（删掉行号仍能定位）
- [ ] 现状 vs 基线冲突处有明确裁决（跟随现状/向基线靠拢/标 OPEN）
- [ ] **无任何本机绝对路径**：记忆里（尤其 INDEX 的流程指引）不出现 skill 安装路径 / agent 运行路径；流程只写动作本身，证据路径用项目内相对路径（见 `core/memory/document-tree.md` §4）
- [ ] INDEX 短且指向全部文档；条目有稳定 id 可定位
- [ ] status.md 有当前阶段/进展/健康度/最近变更，**且最近变更只记项目本身的重要变更、无一次性排查插曲**（见 `core/memory/document-tree.md` §5）
- [ ] open-questions.md 在记忆目录内，问题带证据/日期，**等级（实测/推断/用户约定）与核实状态（已复核/待复核）分列不混写**、有"待协商"小节（见 §6）
- [ ] 闭环可用：写码前能按 `core/memory/retrieval-and-writeback.md` 检索到规范
**内容完成度判据（硬 · 防"建了空骨架就算建完"）**：建库是否完成，按**内容达标**判定，不按"目录存在"判定——规范层五件套条目数 ≥ 12 条 **且** `.project_memory/tmp/PLAN.md` 已落盘，才算建库完成。刚 init 出的空骨架/模板桩不算完成：写完空骨架后不得切到"写码前检索套用"模式而撤掉通读与落盘指令，否则后续全靠自觉、必偷懒。

量化门槛（自检逐条核）：
- RULE 占比 ≥ 35%（只有 FACT 项目照片、没有可套用规则的库判不合格）；
- 高频动作（新增模块/接口/数据/构建目标等）≥ 3 条配方式 RULE，每条写清"抄哪个文件 → 改哪几处 → 怎么验证"，验证步骤不可省；
- 证据主体是"文件路径 + 模式描述"，行号只在括号内辅助（删掉行号仍能定位）；
- 清单式计数（"有 N 个模块"）一律改写成规律；
- `open-questions.md` 里每条 bug/未决必须是 `[OPEN BUG-NN]` 五件套（含证据行/记录行/状态行），禁止散文列表（散文进不了检索）；
- 禁把本 skill/工具的自身实现（如 `.engineering-craft` 标记、init 产物）写成项目约定（幻觉条目）；
- 自检结论给一个 0–100 质量分，< 60 判不合格、回对应步骤补。

不合格 → 回对应步骤补，不带缺陷离开建库环节。

**末步 · 汇入需求循环**：转入 `workflows/feature.md` 第 1 步（需求澄清）。建库不是终点，不在此处停下。

## 多 agent 混合策略（平衡输出一致性与成本）

| 阶段 | 策略 | 理由 |
|---|---|---|
| 通读（最贵） | lead 先定"读法地图"（切批 + 每批必挖维度统一）；再派**只读**子代理并行读不同批次，各回传"模式候选 + 证据路径"的结构化清单 | 并行省 wall-clock；统一清单让各 agent 输出**同构**，这是解决"输出不同"的关键——框定输出格式，不自由发挥 |
| 规划（结构决策） | **lead 独占**，不并行 | 结构是全局一致性问题，多 agent 会各自为政；也让"agent 自定结构"有单一决策者可审 |
| 落盘 + 自检 | lead 写；可派 1 个只读核对代理独立核，lead 逐条核实其输出（不盲信自述） | 自检是判断性工作，一个独立视角够 |

**成本控制**：并行度上限 4 个子代理，多余批次排队；子代理禁止直接写记忆目录（写是 lead 的活，防并发冲突与格式漂移）；覆盖率靠文件清单 diff 机械核对，不靠自述。预算紧时退化成单 agent 分批读——**降级不是失败**，链条不断。

## 三种起点的汇合

空项目（分支 2）在此定语言栈；有代码无记忆 / 代码与记忆都在两种沿用或协商变更已有约定。判定只影响通读/规划怎么做，不影响落盘与汇入需求循环。注意三分支的**分流规则见上文「起点路由」**（有代码无记忆=直接建库不问、空目录/已有记忆=才问，且都发生在强制前置的根确认之后）。

## 完成检查

- [ ] 项目根已**问过用户**（强制前置，发生在目录状态判断之前），确认前未写任何文件；所有写入都在已确认的项目根内
- [ ] 根确认后按三分支正确分流：有代码无记忆=直接建库不问、空目录/已有记忆=才问；没被源码注释里的流程字眼误导
- [ ] 目录名冲突时没往别人的目录写（检查 `.engineering-craft` 标记）
- [ ] 6 个标准职责目录 + 3 根文件齐全，顶层按职责分目录、目录内按子系统分篇，没有被拍平
- [ ] status.md（项目状况）与 open-questions.md（框架问题）都已建且在记忆目录内
- [ ] build/ 按项目实际构建方式分文件（cmake/cargo/pnpm/setuptools/…），未与 architecture 混
- [ ] 每条规范五件套齐、清单式陈述 0 条、高频动作有配方
- [ ] 自检清单全过且附具体证据，质量分 ≥ 60；内容完成度达标（五件套条目 ≥ 12 且 tmp/PLAN.md 已落盘），不以"目录存在/刚 init"当建完
- [ ] 末步接上 `workflows/feature.md` 需求澄清，没断链
