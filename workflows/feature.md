# 编排：新功能（需求到交付）

1. **需求澄清**：三句复述 + 四问 + 验收标准（见 `core/requirements.md`）。写不出"什么算做完了"→ 只问一个问题，不猜。
2. **G1 门（需求门 · 硬）**：核对 PRD 存在、验收标准可判定、且**人已确认**；不满足 → **停在此处，向人要需求，禁止进入第 3–5 步，尤其禁止写任何实现代码**（P0 第 9 条）。门按 G1→G2→G3 顺序推进、禁止倒序（G2 须 G1 已过、G3 须 G2 已过）；G1/G2 由人拍板、agent 不得自报确认，G3 由 agent 凭红灯+证据自检放行。
3. **现状勘察**：读工程记忆 + 读要改的代码及其调用方 + **读对应语言规范**（`languages/`）。读工程记忆时按 `core/memory/retrieval-and-writeback.md` 的检索线索做法，取本次模块 + 横切关注相关的规范条目。
4. **方案设计**：模块划分/数据流/接口契约/异常路径；非平凡设计写双草图（见 `core/design-principles.md`）；复杂方案先给用户确认。
5. **G2 门（设计门 · 硬）**：核对 ADR + 接口契约已落盘、人已确认技术选型；不满足 → **停在方案，找用户确认，禁止开工写代码**（须 G1 已过才可确认 G2）。
6. **计划分解**：编号 3–10 步，每步一动作 + 可判定验收，写入 `.project_memory/tmp/PLAN.md`（执行计划是临时产物，不进规范层；见 `core/memory/document-tree.md` §7）。每个单元记 `{目标, 独占文件清单, 验收, 约束条目 id}`；多个单元并行时 ownerFiles 须按实际落盘语义归一化后互不重叠。
7. **编码实现**：遵循语言规范与工程记忆约定；注释按分层规则（见 `core/coding-standards.md`）；小步提交、每步可编译。**写码前先把第 3 步检索到的规范条目列进 PLAN.md 作为约束清单，编码时逐条对照**（检索套用细则见 `core/memory/retrieval-and-writeback.md`）——这是"按项目已有写法写"的落地点，不可跳过。**写新增/修 bug 的实现前先按 `core/testing-strategy.md` §2 写失败测试、看到它失败并记红灯；没有红灯记录不得写实现**（P0 第 10 条）。本工作流是新功能（改变行为），走红灯路径；行为保持型重构走 `workflows/refactor.md` 的基线绿路径。实现写到可编译后，**立刻跑一次编译/窄检命令，把「命令 + 输出摘要 + 日期」落进 `.project_memory/tmp/VERIFY-LOG.md`**——这条是过 G3 的证据，不要等到 step 10 的全套验证才落（否则 G3 无证据可核）。
8. **G3 门（编译/窄检 + TDD + 证据 · 硬）**：核对 ① 代码可编译、窄检/类型检查通过；② 有 TDD 红灯记录（失败测试指针+红灯输出）；③ `.project_memory/tmp/VERIFY-LOG.md` 有 step 7 落的那条编译/窄检证据（命令+输出摘要+日期）。三项缺一即 **G3 未过：既不可测试、也不送审**，补做后重核（P0 第 9/10/11 条）。G3 只卡红灯与窄检证据；绿灯（测试转绿）在 step 9 记，不阻塞 G3。
9. **测试**：新增逻辑的单元/集成测试，覆盖正常/边界/异常（见 `core/testing-strategy.md`）；改完跑测试转绿并记绿灯输出。
10. **验证**：窄检→全套→贴输出；每条真实命令落进 `VERIFY-LOG.md`；证据分级（见 `core/verification.md`）。"上次跑过/子 agent 说通过/我很有信心"不算证据（§4.1 红线）。
11. **联调（按需）**：多模块/服务拼起来验证时走 `core/integration.md`（契约对齐、端到端通路）；单模块跳过。
12. **用户验收（按需）**：交付前对照 PRD 验收标准逐条核，走 `core/acceptance.md`；用户不在场标"自验待确认"。
13. **评审自审**：范围/diff/findings，4 轮封顶（见 `core/review.md`）。
14. **交付**：交付说明 + PR（见 `core/delivery.md`）；规范有变写回工程记忆。
15. **发布（按需）**：涉及上线部署时，先走 `core/release-and-operate.md`（发布三件套 + 人做 go/no-go + 上线观察）；不涉及则跳过。
16. **追问**：完整流程走完后，问下一需求 + 是否需要调整修正，然后停下（见 SKILL.md 第六节）。**若本轮用户提的是新需求（不是对上一需求的追问/收尾），不得复用上一需求"已完成"的结论直接开工——重新走完整流程**，不沿用上次的门状态与交接物当"已过"。
