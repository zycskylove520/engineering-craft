# 编排：多 agent 并行开发（能力感知 · 条件启用）

> 适用：任务可拆成 ≥2 个文件归属不重叠的独立单元，且当前 agent 环境提供委派工具。这是 `workflows/feature.md` 的**可选加速路径**，不是默认路径。
>
> 来源：2026-11-23 方案二。依据：工具集与 workflow 使用规则为实测（本会话）；三道门/三态路由为推断（基于已读的 MetaGPT、Agentic SDLC Handbook ch4、ACDL、OpenHands 工作流横评）。**尚未在真实多 agent 任务上跑过，不宣称已验证可行。**

## 0. 核心原则（先立规矩）

**角色是流水线（顺序门），任务是并行单元。** SKILL.md §2.1 的五环节——产品→架构→研发→测试→运维——必须按序过门，不能把五个角色拆成五个 agent 同时跑；那会让研发在架构的 ADR 出来前就写代码，交接物断链。并行只发生在**同一阶段内部、文件归属不重叠的独立单元**（模块 A / 模块 B 分头改）。

## 1. 三道门（全过才并行）

| 门 | 判据 | 不满足时 |
|---|---|---|
| **能力门** | 有 `subagent` / `subagent_fork` / `workflow` + 消息工具；且策略允许（见 §2 三态路由） | → 单 agent 顺序执行（一等路径，不是降级、不道歉） |
| **任务形状门** | ≥2 个独立单元；文件归属不重叠；每单元有可判定验收标准 | → 顺序执行，不制造假并行 |
| **收益门** | 任务够大，能摊平上下文重复、协调、合并与集成验证的成本 | → 单 agent |

**反例（禁止并行）**：TDD 修 bug（红→绿→重构是强因果链）；单文件小改动；强顺序依赖（B 必须读 A 刚写的文件才能开始）；产出只是文档/闲聊。

## 2. 三态路由（能力是必要不充分）

1. **无工具 / 小改动 / 强顺序** → 单 agent 走 `workflows/feature.md`。
2. **有 subagent + 独立单元** → 主 agent 在**一条消息里同时起多个 subagent**（真并行），自己继续做集成准备；1–2 个委派优先普通 subagent，不用 workflow。
3. **用户明确要求 + 大规模多阶段编排** → 才用 `workflow` 脚本（`workflow` 工具规则：仅在用户显式要求或大规模编排时使用，不自主启用）。

> 能力检测踩坑：工具"存在"不等于"策略允许"。路由第 3 态必须有用户明确要求，否则即使工具在也走第 2 态。

## 3. 执行流程

1. **前置流水线（单 agent 做，顺序）**：需求澄清 → **G1 需求门** → 现状勘察 → 方案设计 → **G2 设计门（架构选型用户确认）** → 计划分解。沿用 `feature.md` 第 1–6 步（含两道硬门检查）。**G1/G2 未过禁止并行委派、禁止任何子 agent 写实现代码**（P0 第 9 条）；交接物齐了才进并行。
2. **拆单元**：按"文件归属"切分，写入 PLAN.md：每单元 = 目标 + 独占文件清单 + 验收标准 + 对应语言规范。**单元之间文件不重叠**；重叠的合并进同一单元或串行。
3. **并行委派**：一条消息内同时调用多个 `subagent`。每个子 agent 的 prompt 自包含：共享交接物（PRD/ADR/接口契约摘要）+ 对应语言规范路径 + 它的单元目标与验收 + "产物落盘、不要口述汇报"。**不灌整段聊天**。
4. **主 agent 集成准备**：子 agent 跑的同时，准备集成验证脚本、review brief 骨架、合并顺序——不重复子 agent 的活。
5. **收结果**：等所有子 agent 完成；产物以落盘文件为准，消息里的"我完成了/我测过了"只当提示。**任何子 agent 输出都不自带"已通过"**。
6. **集成验证（主 agent 重跑）**：合流 → 跑窄检→全套（见 `core/verification.md`）→ 贴真实输出 → 证据分级。子 agent 各自测过不算数，集成后必须重跑。
7. **评审自审**：`core/review.md` 的 Brief + findings，4 轮封顶；最终 diff 由主 agent 把关。
8. **回退**：某单元失败（返回 null / 产物不合格 / 验收不过）→ **只把该单元回退给单 agent 重做**，其它单元成果保留；连续 2 次失败攻前提（见 `core/verification.md`），停下列出阻塞。
9. **交付**：`core/delivery.md`；规范有变写回工程记忆。
10. **发布（按需）**：涉及上线时先走 `core/release-and-operate.md`（人做 go/no-go）；否则跳过。
11. **追问**：完整流程走完后，问下一需求 + 是否需要调整修正，然后停下（见 SKILL.md 第六节）。

## 4. 交接物契约（复用 SKILL.md §2.1）

并行 agent 之间的接口就是方案一的交接物表，**不新造协议**：

- 上游交接物（PRD/ADR/接口契约）落盘成文件，子 agent 读文件而非听口述——结构化交接降低幻觉（MetaGPT 核心洞察）。
- 子 agent 产物落盘（代码 + 测试 + 该单元的验证输出），汇报只给路径指针。
- 主 agent 收齐后按路径核对，不靠子 agent 自述判断完成。

## 5. 失败模式清单（必须防）

- **多 agent 改同一文件** → 互相覆盖 ⇒ 按文件所有权切分，重叠即串行。
- **子 agent 看不到别人产物** → 交接物落盘，消息只传指针。
- **子 agent 失败返回 null** → 按单元回退单 agent，不让整条流水线崩。
- **只信"我测过了"** → 主 agent 重跑全套验证。
- **上下文过半** → 回退到 `core/operations.md` 的 PROGRESS.md 接力（状态写文件，不写聊天）。
- **为并行而并行** → 三道门任一不过就单 agent，不道歉、不硬拆。

## 6. 完成检查

- [ ] 三道门全过才并行；未过门却并行 = 设计错误？
- [ ] 角色仍按流水线顺序过门，未把五环节同时跑？
- [ ] 单元按文件归属切分、不重叠，每单元有可判定验收？
- [ ] 交接物与子 agent 产物都落盘，汇报只给路径指针？
- [ ] 集成后主 agent 重跑全套验证并贴真实输出，未采信子 agent 自述？
- [ ] 失败单元按单元回退，连续 2 次失败攻前提？
- [ ] workflow 脚本仅在用户明确要求/大规模编排时使用？
