# 编排：多 agent 协同开发（顺序岗位流水线 + 条件并行）

> 适用：任务需要多个 agent 分岗协作。这是 `workflows/feature.md` 的多 agent 形态，覆盖两种形状：
> **形态 A——顺序岗位流水线**（角色=岗位，交接物驱动，岗位间严格顺序；可整条流水线恒用，也可某任务全程用）；
> **形态 B——同阶段条件并行**（一个岗位内部按文件所有权切成互不重叠的单元并行）。
>
> 来源：2026-11-23 方案二（工具集/三道门为当时推断）。**2026-11-23 由真实工程任务完整实跑验证并修订**：形态 A 跑通产品→架构→研发→测试→评审→运维六岗位，形态 B 与「回退上游 / 架构收敛 / 端到端强制」均来自实测踩坑。原"尚未在真实多 agent 任务上跑过"免责声明作废。

## 0. 核心原则（先立规矩）

**角色按交接物依赖顺序过门；并行只发生在同一交接物版本内、文件归属不重叠的单元。** 绝不把"有依赖的岗位"拆成并行——那会让下游读到半成品交接物；也绝不因为"有 subagent 工具"就默认拆碎。

**硬门优先于委派**：G1/G2 未过禁止任何子 agent 写实现代码，**G3 未过禁止送审**（P0 第 9 条）。并行/流水线都是交接物齐备之后的组织方式，不是绕过门的捷径。

## 1. 两种形态与岗位并行分类

### 1.1 形态 A：顺序岗位流水线（默认在此形态里讨论角色）

| 岗位 | 本质 | 并行性 | 判定理由 |
|---|---|---|---|
| 产品 → 架构 | 严格因果：架构的输入就是 PRD | **禁止并行** | 没有 PRD 就没有 ADR 的输入，强行并行=凭空猜 |
| 研发 | 输入 ADR+CONTRACT；内部按文件所有权可切单元 | **条件并行**（见 §1.2 三道门） | 同一契约下多模块互不重叠时可分头写；上游一改全部冻结回退 |
| 测试 | 用例设计可基于 CONTRACT 提前；"跑出结论"必须等代码冻结 | **部分并行**：用例准备可与研发尾段重叠，结论不可 | 基于契约写边界清单不依赖实现；但结论依赖最终代码 |
| 评审 | 必须看最终 diff + 真实测试输出 | **禁止并行** | 半成品上评审会基于不完整的证据下结论 |
| 运维/发布 | 依赖 APPROVE 与人拍板 | **禁止并行** | go/no-go 是人的决定，无并行前提 |

**一句话**：**岗位之间按依赖严格顺序；只有研发内部、测试准备阶段允许条件并行。**

### 1.2 形态 B：同阶段条件并行（三道门）

| 门 | 判据 | 不满足时 |
|---|---|---|
| **能力门** | 有 `subagent`/`subagent_fork`/`workflow` + 消息工具，且策略允许 | 退回顺序执行（单 agent 是该岗位内的一等路径，不是降级、不道歉） |
| **任务形状门** | ≥2 个单元；文件归属不重叠；每单元有可判定验收 | 顺序执行，不制造假并行 |
| **收益门** | 任务够大，能摊平上下文重复、协调与合并成本 | 顺序执行 |

**反例（禁止并行）**：TDD 修 bug（红→绿→重构强因果）；单文件小改动；强顺序依赖（B 必须读 A 刚写的文件）；产出只是文档/闲聊；**契约还在变**（见 §5.1 冻结规则）。

## 2. 路由（先定形态，再定并行）

**先看是否需要多 agent 编排，再看是否并行：**

1. **单 agent 够用**（无委派工具 / 小改动 / 紧耦合无交接物，如 TDD 红→绿→重构）→ 走 `workflows/feature.md`，单 agent 是本岗位内的一等路径（不道歉）。
2. **需要多 agent、但当前岗位无独立单元**（角色间是交接物依赖，如产品→架构）→ **形态 A：顺序岗位流水线**。这是多 agent，只是岗位间不并行。若某岗位（如研发）内部拆出互不重叠单元，再在该岗位内启用形态 B。
3. **同一岗位内有 ≥2 个文件不重叠的独立单元**（三道门全过）→ **形态 B：一条消息同时起多个 subagent**，lead 继续做集成准备；1–2 个委派优先普通 subagent，不用 workflow。
4. **用户明确要求 + 大规模多阶段编排** → 才用 workflow 脚本（仅显式要求/大规模编排时使用，不自主启用）。

> 能力检测踩坑：工具"存在"不等于"策略允许"。第 4 态必须用户明确要求。**"强顺序"指紧耦合不可分单元（第 1 态），不等于"角色流水线"（第 2 态也是多 agent）**——这是本次修订的关键边界。

## 3. 执行流程（两形态共用骨架）

1. **前置流水线（lead 顺序做）**：需求澄清 → G1 → 现状勘察 → 方案设计 → G2 → 计划分解。沿用 `workflows/feature.md` 第 1–6 步。G1/G2 未过禁止委派写码。
2. **定形态**：按 §2 路由判断走单 agent / 形态 A / 形态 B / workflow，或组合（A 为骨架，研发岗内部启用 B）。
3. **拆单元**：B 形态按文件所有权切分写入 PLAN.md：每单元 = 目标 + 独占文件清单 + 验收 + 对应语言规范；单元文件不重叠。
4. **委派**：用**独立上下文 subagent**（`subagent`，prompt 自包含），不用 `subagent_fork` 继承整段聊天。prompt = 共享交接物路径 + 语言规范路径 + 本单元目标与验收 + "产物落盘、汇报只给路径指针"。**不灌整段聊天**。
5. **lead 集成准备**：子 agent 跑时准备集成验证脚本、review brief 骨架、合并顺序——不重复子 agent 的活。
6. **收结果**：产物以落盘文件为准；子 agent 自述的"我完成了/我测过了"只当提示，自带"已通过"不算数。
7. **G3 检查（命名硬门）**：窄检/类型检查未过不得往下走；**G3 未过禁止送审**（对齐 SKILL P0 第 9 条、`workflows/feature.md`）。
8. **集成验证（lead 重跑）**：全套→**端到端业务路径**（见 §6"写后能读到"）→贴真实输出→证据分级。
9. **评审自审**：`core/review.md`；4 轮封顶；diff 由 lead 把关；APPROVE 附带的 should/nit 按 §4.5/§4.6 逐条收口。
10. **回退**：按 §5 处理（失败单元 / 上游交接物缺陷 / 环境契约失效）。
11. **用户验收（按需）**：`core/acceptance.md` 对照 PRD 逐条核；用户不在场标"自验待确认"。
12. **交付**：`core/delivery.md`；规范有变写回工程记忆。
13. **发布（按需）**：涉及上线先走 `core/release-and-operate.md`（人做 go/no-go），否则跳过。
14. **追问**：完整流程走完后问下一需求 + 是否有需调整修正，然后**停下等回复**。

## 4. 交接物契约（复用 SKILL.md §2.1）

- 上游交接物落盘成文件，下游读文件而非听口述。
- 子 agent 产物落盘（代码+测试+验证输出），消息只传路径指针。
- lead 按路径核对，不靠自述判断完成。
- **事实等级标注**：接口契约中每条外部 API 声明按 `topics/api-design.md` §6 的五级体系标注（`[实测]`/`[实测纠正]`/`[交接]`/`[设计]`/`[待实测]`，完整定义以该节为准，此处不复述）。凡 `[待实测]` 必须登记进 `open-questions.md`，**不得臆造 API 带病写码**。实测：CONTRACT 用此标注后，lead 一眼识别哪些是假设，及时退回架构岗纠正，避免带着错契约写实现。

## 5. 回退与冻结（实测补强）

### 5.1 上游交接物缺陷 → 退回上游、冻结下游

下游或 lead 发现**上游交接物本身有错**（契约 API 假设错误、设计自相矛盾），不是下游实现的锅：
- **冻结所有下游并行单元**，停止基于该版本继续写；
- 退回产生该交接物的岗位修订，写明缺陷证据与要改的节；
- 交接物自洽后，下游才解锁；期间下游不"先按假设写着"。
- 实测：CONTRACT 的 4 处 API 假设被推翻，退回架构岗修订后才放研发岗上工——若当时硬写，代码会建立在错 API 上。

### 5.2 失败单元

某单元失败（返回 null / 产物不合格 / 验收不过）→ **只把该单元回退重做**，其它单元成果保留；连续 2 次失败攻前提（`core/verification.md`），停下说明阻塞。

### 5.3 契约无法实测 → 架构收敛到已验证替代

因**环境/工具限制**（非代码 bug）导致契约测不了（例：本轮 cordis 带参查询被 harness 层一律拒绝），按 unstick 换路径后仍不可得：
- 不猜 API、不无限攻前提；
- 收敛到**已在本机/生产验证过的替代机制**，在 ADR 记录"原设计→收敛后→证据"；
- 把"仍待真机验证"诚实写进交付说明。
- 这与"缩范围作弊"不同：是换一条可验证的路，不是降低验收标准。

## 6. 完成定义（新增硬条）

- [ ] 岗位按 §1 依赖顺序过门；形态按 §2 路由选定，可并行的岗位满足三道门且文件不重叠？
- [ ] G3 已作为命名硬门检查，未过未送审（对齐 SKILL P0 / `workflows/feature.md`）？
- [ ] 上游交接物有缺陷时已冻结下游并退回上游修订？
- [ ] 交接物/产物落盘、汇报只给路径指针；公开 API 标了事实等级、`[待实测]` 进了 open-questions？
- [ ] 契约不可测时走了 §5.3 收敛并在 ADR 留痕，未臆造 API？
- [ ] **lead 集成重跑窄检+全套，并端到端跑通关键业务路径**——尤其每类"状态写入"要验"写后能读到"（见 `core/integration.md`）？
- [ ] 评审 APPROVE 附带的 should/nit 逐条标明修/已知限制，lead 收尾改动已重跑验证并留痕（见 `core/review.md` §4.5/§4.6）？
- [ ] 用户验收（按需）逐条有输出；交付说明齐；涉及上线时发布清单/回滚预案/观察项齐且 go/no-go 由人拍板；追问后停下？
- [ ] 失败单元按单元回退、连续 2 次失败攻前提？
- [ ] workflow 脚本仅在用户明确要求/大规模编排时使用？

> 为什么强调端到端：实测中 5 个缺陷（交接物落盘却未登记指针、确认返回裸路径串、两个确认卡恒假条件、面板 handoffs 键错位）**全部是单测与窄检测不出、端到端业务路径才暴露**的。岗位说"测过了"不等于系统通了。

## 7. 失败模式清单

- 多 agent 改同一文件 → 互相覆盖 ⇒ 按文件所有权切分，重叠即串行。
- 子 agent 看不到别人产物 → 交接物落盘，消息只传指针。
- 子 agent 失败返回 null → 按单元回退，不让整条流水线崩。
- 只信"我测过了" → lead 重跑全套 + 端到端关键路径。
- 上游交接物有错却让下游继续 → 冻结下游、退回上游（§5.1）。
- 契约测不了就猜 API → 收敛到已验证替代 + ADR 留痕（§5.3）。
- 上下文过半 → 回退 `core/operations.md` 的 PROGRESS.md 接力（状态写文件，不写聊天）。
- 为并行而并行 → 三道门任一不过就顺序执行，不道歉、不硬拆。
