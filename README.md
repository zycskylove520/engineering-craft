> 语言：[中文](./README.md) · [English](./README.en.md)

一个通用的 agent skill：让代码工程变成**有纪律、可验证、能积累**的过程。需求没确认不写码、设计没确认不开工、检查没过不送审；每一步都有真实命令和输出作证据，项目的规范与决策跨会话沉淀在 `.project_memory/` 里。

**不绑定任何 agent 软件**：全部是 Markdown，没有代码、构建或私有 API——任何能加载 skill 目录的 agent 都能用。

## 它解决什么

- 需求没澄清就写码，做到一半发现方向错了
- 改完只说"应该没问题"，拿不出真实命令和输出
- 项目规范散在聊天里，换个会话就丢
- 小任务太重、大任务太糙，一套流程走天下

## 安装

把整个目录放到 agent 加载 skill 的位置，重启会话（或触发技能重载）即可。

| Agent | 常见 skills 目录 |
|---|---|
| Claude Code | `~/.claude/skills/` 或项目 `.claude/skills/` |
| Cline / Roo Code | 项目的自定义指令目录（如 `.clinerules/`） |
| 其他支持 skill 的 agent | 该软件的 skills / 指令目录 |

```bash
git clone https://github.com/zycskylove520/engineering-craft.git
# 把 engineering-craft/ 整个目录复制到你的 agent 的 skills 目录
```

> 入口是带 YAML frontmatter 的 `SKILL.md`；若你的 agent 用别的入口约定，只需指向入口文件，内容无需改动。

## 怎么触发

说**「开始工程」**（精确四个字）；日常写代码、改 bug、调试、重构、审查代码时它也会按描述自动加载。

触发后第一步**先问你一句**：是否在 `<当前会话所处目录>` 进行工程构建——默认候选取当前会话目录（不是 agent 软件自己的运行目录），你确认或换一个路径后才开工，避免把工程建错地方。

## 三种使用场景

### 1. 初次使用（空项目）

对 agent 说「开始工程」，告诉它你要做什么。它会先和你商谈**架构、语言、命名、技术栈**——不凭空替你决定——把约定落成项目里的规范文件，再进入需求澄清。你只需要回答它的问题、在关键处拍板。

### 2. 融入已有项目

- **已有代码、尚无记忆**：它会分批通读源码，自己决定文档怎么分（按"以后写代码时怎么找"来组织，可嵌套），沉淀出可套用的写法规范——每条带路径证据、写"规则"不写"清单"；主动指出不合理设计并和你协商，然后建起 `.project_memory/`。不擅自大改。
- **代码和记忆都在**：它先读 `INDEX.md` 和规范，按项目既有约定干活，不重写你的规矩。**写业务/核心代码前会先检索相关规范，照已有写法写**；产生的新模式经验证有效才写回记忆。
- **不想全量启用**：小改动可裁剪流程，但"需求没明确就不写码"这条不变。

### 3. 下一次使用

不用重新讲一遍项目背景。直接说「开始工程」+ 新需求，它会读已有记忆接着上次的约定走；每次交付后如果有长期约定变化，会写回规范层，下次自动生效。

## 运行原理（概览）

复杂任务按六个岗位推进，每个岗位各司其职：

| 岗位 | 它为你做什么 | 完成后给你什么 | 谁拍板 |
|---|---|---|---|
| 产品 | 把你模糊的想法问清楚，整理成有验收标准的需求 | 一份需求文档（目标 / 用户故事 / 优先级） | **你**：确认验收标准 |
| 架构 | 基于定好的需求设计初版结构，选语言和技术栈 | 架构决策 + 接口约定 | **你**：确认技术选型 |
| 研发 | 按计划一小步一小步写代码，每步都能编译 | 可运行的代码 + 执行计划 | agent 自检通过即可 |
| 测试 | 写测试、跑边界情况、贴出真实命令输出 | 测试报告 + 可核查的运行证据 | agent 自检通过即可 |
| 评审 | 回看改动与证据，找问题、提修法 | 评审结论 + 问题清单 | agent 自审；有争议请你定 |
| 运维 | 准备上线材料与回滚方案 | 发布清单 + 回滚预案 + 观察项 | **你**：go/no-go |

六个岗位按交接物依赖**严格保序**：上游的东西落盘了，下游才开工；只有同一岗位内部出现文件互不重叠的独立单元时才会**条件并行**。上游交付有问题会冻结下游、退回重做，不让错误往下传。

**常规流程有三个固定拍板点**（表内加粗标出）：确认需求验收、确认技术选型、涉及上线时的 go/no-go；另有一个条件触发点——评审出现争议时由你定夺（表中评审行已标）。其余由 agent 按纪律推进。

**如果你的 agent 软件不支持多 agent 协同**：不影响使用。同一个 agent 会按顺序扮演这六个岗位，把中间产物写成文件、下一阶段读文件继续；保序、门、验证与记忆沉淀全部照旧，只是没有并行带来的速度提升。这不是降级运行，是同一套纪律的单线程形态。

它是一套**纪律与可验证性**，不是系统级强制 hook：能让违规和未经验证的断言显眼可查，但不能物理阻止 agent 绕过流程。

运行原理与工程记忆的完整规范见 `SKILL.md`；六岗位细节见 `workflows/multi-agent-feature.md`。

## 适用范围

**适合：**
- 有一定规模或需要多人 / 多 agent 协作的代码工程：新功能、重构、跨模块改动。
- 需要长期维护的项目，规范与决策要跨会话积累、不随聊天丢失。
- 需要可审计过程：谁确认了需求、谁拍板了选型、断言有没有真实输出，都要有据可查。
- 代码质量与过程纪律比"最快出活"更重要的场景：生产代码、开源项目、团队项目。
- agent 软件支持 subagent 时，可让六岗位真正分头协作；不支持也能单 agent 顺序走完全程（见「运行原理」）。

**不适合 / 按需裁剪：**
- 纯闲聊、查资料、写文档等非代码任务：本 skill 不触发。
- 一次性小改动（改错别字、调常量）：不必留全套交接物，按需裁剪到最小。
- 强顺序的紧耦合任务（如 TDD 红→绿→重构）：走单 agent，不强行并行。
- 期待系统级强制拦截的场景：它是纪律而非 hook，不能物理阻止 agent 绕过流程。

## 目录结构

```
engineering-craft/
├── SKILL.md              # 薄入口：导航、红线、工程记忆
├── README.md / README.en.md
├── core/                 # 通用规范：需求、设计、编码…；含 memory/ 工程记忆能力簇
│   └── memory/           # 内容模型 / 目录组织 / 使用闭环（文件名即能力）
├── workflows/            # 编排流程：首次建库 / feature / bugfix / refactor / 多 agent…
├── languages/            # 语言规范：写码前读对应一篇
├── topics/               # 横切专题：安全 / 性能 / 并发 / API 设计…
└── CHANGELOG.md / LICENSE
```

**目录约定式**：每层 INDEX 只声明"文件名即适用信号"的读取协议，不再逐个登记文件——新增工作流、能力、语言或专题只需新建文件，**不改任何索引**。
