# API 设计（横切专题）

## 1. 契约先行
- 先定接口契约（签名/类型/协议/错误语义），再写实现。
- 公开面越小越好；内部实现可自由重构，公开契约要稳定。

## 2. 兼容性
- 新增字段兼容旧客户端；删除/改语义要版本化或迁移路径。
- 破坏性变更明确版本号与弃用周期；给调用方迁移时间。

## 3. 语义清晰
- 命名表达意图；参数/返回值/异常有明确约定（写进注释，见 `core/coding-standards.md`）。
- 幂等性：重试不产生重复副作用（尤其写操作、消息、支付）。
- 错误结构统一：错误码/消息/上下文一致，可机器处理。

## 4. 边界与校验
- 输入在边界校验；输出稳定不暴露内部实现。
- 超时、分页、限流等横切约定一致。

## 5. 文档与测试
公开 API 必有文档（硬要求）；契约测试覆盖正常/边界/错误；示例可执行。

## 6. 外部 API 声明的事实等级（2026-11-23 实测）

**与"证据分级"的区别（先读）**：`core/verification.md` 的「实测 / 推断 / 猜测」是对**结论与验证结果**分级；本节五级标签是对**接口契约中的外部 API 声明**分级。两者作用域不同、不可混用：前者回答"这个结论有多可信"，后者回答"这条外部 API 能不能当真去写代码"。大致映射：`[设计]` 类似"推断"（本工程定的、待验证），`[待实测]` 类似"猜测"（不可据此写实现），但**不要互相替代用词**——契约里写标签，验证报告里写结论等级。

写接口契约时，凡引用**不属于本工程、来自外部系统/框架/服务的 API**，每条声明标注事实等级，防止把假设当事实写进实现：

- `[实测]`：本轮工具探测、源码阅读或可运行探针确认过。
- `[实测纠正]`：推翻了早期假设并据以修订，附证据路径（何时、被什么事实推翻）。
- `[交接]`：上游已核实的外部事实（注明来源）。
- `[设计]`：本契约自己定义、尚待实现验证的约定。
- `[待实测]`：**不得据此写实现**；必须登记进 `open-questions.md`（要查什么 / 用什么手段 / 卡住哪个交付物 / 何时必须定），查证后再升级为其他等级。

**为什么硬要求**：实测中契约文件把某外部工具的注册 API 签名当成既成事实写死，实际签名完全不同；若研发照着写，代码会建立在错 API 上。标了等级后 lead 一眼识别哪些是假设，及时退回上游纠正。**契约可标假设，实现不可带病写。**

> 边界：这是通用工程纪律，不绑具体框架。某框架的具体 API 写法属于项目自己的 CONTRACT/工程记忆，不写进本 skill。
