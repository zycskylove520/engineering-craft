# 跨模块联调

> 适用：多个模块/服务/前后端改动需要拼起来验证的场景；单模块改动按 `core/testing-strategy.md` 的集成测试即可，不必走本文件。来源：2026-11-23 补联调缺口。
>
> 与相邻规范的分工：`core/testing-strategy.md` 管测试代码与覆盖率（代码层）；`core/verification.md` 管单改动的验证闭环（改动层）；本文件管**多份改动拼合后的接口对齐与端到端通路**（系统层）。

## 1. 联调前对齐契约

- 逐对列出交互边界：谁调用谁、接口签名/协议/数据形状、错误语义、超时与重试约定（契约见 `topics/api-design.md`）。
- 各方改动必须基于**同一版契约**；发现契约理解不一致 → 停下对齐，不各自按假设实现（这正是 G2 门要防的）。
- 版本/环境/配置对齐：各模块跑在兼容的版本与同一套环境配置上，避免"我这边是好的"式扯皮。

## 2. 拼合验证

- 先窄后全：两两模块联通 → 再端到端跑关键路径；每步贴真实输出，不靠口述"应该没问题"。
- 覆盖三类通路：正常主流程 / 边界数据 / 一方失败时另一方的行为（错误传递、降级、超时）。
- 数据与环境：用可复现的最小数据集与固定环境，不依赖生产数据或偶然状态；联调结束清理临时数据。

## 3. 问题定位（联调特有）

- 出问题先定位在哪一方的边界：用探针（日志/请求响应快照/`which`/`--version`）给 yes/no，不凭"应该是那边"甩锅（见 `core/verification.md` unstick）。
- 契约问题回 G2（设计未对齐），实现问题回 G3（代码未达交接标准），环境问题记入 Key facts；不靠临时补丁绕过根因。
- 多方都在改时，先冻结一方的改动再定位另一方，避免变量同时变化。

## 4. 记录与交接

- 联调结果写成可审文本（工作区临时产物）：参与模块/版本、契约版本、测试用例与真实输出、发现的问题与归属、最终结论。
- 形成的长期约定（如接口约定、环境约定）写回工程记忆规范层（见 `core/project-memory.md`），原始流水不写。

## 5. 完成检查

- [ ] 交互边界与契约版本逐对确认，各方基于同一版契约？
- [ ] 两两联通 + 端到端关键路径都贴了真实输出，覆盖正常/边界/失败三类通路？
- [ ] 问题按边界定位、回退到对应门，未用临时补丁绕过根因？
- [ ] 联调结果落盘、长期约定写回工程记忆？
