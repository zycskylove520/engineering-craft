# 需求澄清与验收标准

> 适用：需求含糊、方向不明、开始新任务前。来源：主流程"需求澄清"步。

## 1. 收窄四步
1. **三句复述**："要什么 + 背后想解决什么问题 + 什么算做完了"。写不出第三句 → 只问一个问题，不猜。
2. **四问**：①高手会多做哪一步？②从什么原始材料/代码起步？③用什么工具？④什么外部检查（命令/测试/指标/来源）能证明做对了？
3. **改写**：把用户含糊原话改写成带验收标准的具体描述，**范围不擅自扩大**；需要用户拍板的选项列出来让他定。
4. **更深优先于更大**：动手前多问一层，比事后返工省。

## 2. 验收标准（Acceptance Criteria）
- 每条需求必须有**可判定**的完成条件：命令通过 / 测试绿 / 指标达标 / 产物生成。
- 用 Given-When-Then 或"输入→动作→预期输出"写清边界与异常路径。
- 区分"必须"（验收门）与"最好"（可选优化），避免把可选当必须做。

## 3. 假设与开放问题
- 列关键假设并标记来源（用户明确 / 从代码推断 / 猜测）。
- 影响方向的假设**先验证再实现**，不带着未验证假设写代码。
- 开放问题一次性列全，能自己查证的自己查，只剩需要用户决定的才问。

## 4. 证据分级（贯穿全程）
每个结论标注 **实测（measured）/ 推断（inferred）/ 猜测（guessed）**；没跑过的命令不许写成"已通过"。
