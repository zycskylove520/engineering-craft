# 验证与证据

> 适用：改完代码、要说清证据、卡住时。来源：原 8.4 + 8.5。

## 1. 验证闭环
1. **改前**：选最窄的真实检查，记下命令，先跑出基线（先看清它原来什么色）。
2. **改后**：跑同一命令；**读完整报错**——第一条错误、文件与行号、自己代码的栈帧，别跳到末行下结论。
3. 一句话写根因；写不出就加 print 或读失败代码再跑。**修因不修果，一次只改一处**。
4. 窄检过了，再跑全套/构建/lint 一次。
5. 把"命令 + 末几行输出"贴进回复作为交付证据。

## 2. 证据诚信
- 结论标 实测/推断/猜测；未验证不宣称完成。
- 不弱化/跳过/删测试，不 mock 掉被测对象。
- 本套「实测/推断/猜测」是对**结论与验证结果**分级。接口契约里对**外部 API 声明**另有五级标签（`[实测]`/`[实测纠正]`/`[交接]`/`[设计]`/`[待实测]`，见 `topics/api-design.md` §6），作用域不同、不可混用：契约写标签，验证报告写结论等级。

## 3. 爆炸半径自查
找出"这次改动之所以安全"的 1–2 个关键事实，按级别推进——
①口头断言 → ②指到具体文件行 → ③追踪失败路径证明不可达 → ④写脚本对真实代码跑、出错大声失败 → ⑤运行中复现。便宜就推到 ④。

## 4. 失败两次攻前提（unstick）
- 同一修法连续失败两次 → 停下，别试第三次变体。
- 逐行记失败：改了什么 + 确切报错（不写"还是不行"）。
- 写出共享假设（"跑的是这个文件 / 配置被加载了 / 收到的是字符串 / 错误来自我的代码"），用**给 yes/no 的最便宜探针**直接测：print、日志、`which`/`--version`、`grep` 真实调用点、最小脚本、读已装版本文档——贴出结果。
- 假设为假 → 据新事实重规划；为真 → 列 3 条真正不同的方案（换机制/库/层/数据路径），各写成本风险，选一条说明理由。
- 回退残留到干净态再实施；两轮无效 → 如实报告尝试/假设/证据，请用户给方向。

> 能力边界：hook 才能强制的"改完没验证自动打回、失败两次强制换路"本 skill 只能写成纪律，靠自觉。
