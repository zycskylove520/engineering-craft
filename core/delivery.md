# 交付与 PR

> 适用：交付说明、提 PR、合并、接手他人 PR。来源：原 8.8。

## 1. 交付流程
新分支 → 最小改动 → 复现失败 → 修 → 同一复现再跑 + CI → review → rebase → PR → 盯 CI/review → 合并门。

## 2. PR 标题与描述
- 标题写"对用户变了啥、为何重要"（"用压缩把帧降 70%" 优于 "协商 permessage-deflate"）。
- 描述 = 问题（取用户原话）+ 修复 + 一行证明 + 署名；扫一遍密钥与隐私；建为 ready 非 draft。

## 3. 评论规范
结论先行、引用行/检查/复现、区分已验证与观点；一条评论一个归属、无客套、预览后再发。

## 4. 合并门（全真才合）
- 证明覆盖整个 diff
- 必需检查全绿
- review bot 完成
- 每条发现已修或答复
- 无人要求改
- 分支最新可并
自动合并、`--force-with-lease`、后台等 CI 依赖专门工具，无则如实说明由人来执行。

## 5. 接手与旧 PR
- 接手：以 head SHA 和实际文件为准，交接说明只当提示；保留原作者 co-author；新分支 + 独立提交。
- 旧 PR 用证据答五问：问题是否已解 / API·类型·结构是否变 / 代码是否被移动删除简化 / 合并是否引入旧行为或两套做法 / 收益是否仍值维护 → 决定救/改/关。
