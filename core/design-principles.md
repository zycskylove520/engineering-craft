# 设计原则

> 适用：方案设计、架构决策、数据建模、动手写实现前。来源：原 8.3 + 通用工程规范。

## 1. 核心原则
- **单一职责与高内聚低耦合**：模块边界清晰，依赖方向明确（单向依赖，无环）。
- **先减后加**：删死代码/过期检查/无用分支；最短 diff；没有第二个使用者的抽象不建。
- **最小充分改动**：只改必要部分，顺手重构导致范围失控是禁区。
- **一次一件事**：一次只推进一个改动；超过两步用编号清单跟踪。

## 2. 数据形状先行
- 先定类型再写逻辑；用带标签联合/状态机收敛分支。
- 校验只放边界，核心保持纯；让非法状态不可表示。
- 外部数据解析一次成命名类型；`unknown` 不用 `any`，`default` 分支加 `never` 检查（语言无关思想，具体写法见语言文件）。

## 3. 草图先行（非平凡设计）
- 写 ≥2 份**结构不同**的草图：真实文件 + 类型 + 签名 + 抛 not implemented 的桩 + 伪代码。
- 选**公开面更小**、单文件改动对全仓也对的那份。
- 先过类型/check 再填实现；签名变更只能走"修订草图"，不直接改。

## 4. 契约与边界
- 模块间以明确契约（接口/类型/协议）交互，契约变更要考虑兼容性。
- 清晰地盘：哪些是公开面（要稳定、要注释），哪些是内部实现（可自由重构）。

## 5. 决策记录
关键架构决策写入工程记忆 `architecture/decisions.md`，写清"是什么 + 为什么 + 取舍"，带证据。
