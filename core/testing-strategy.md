# 测试策略

> 适用：写测试、TDD、评估覆盖率。框架与写法见语言文件第 8 章。
> TDD 是所有生产/业务代码的强制前置（§2），不是可选方法；详见 `SKILL.md` P0 第 10 条。

## 1. 测试金字塔
- **单元测试**：核心逻辑、边界、异常路径，快且多。
- **集成测试**：模块间协作、外部接口契约。
- **端到端**：关键用户路径，少而精。
- 越底层越快越多，越顶层越慢越少。

## 2. TDD（所有生产/业务代码的强制前置）

TDD **不是可选方法**：**新增逻辑与修 bug** 必须先走红→绿再写实现，它是 G3 的硬前置检查（P0 第 10 条；"太简单不用 TDD"属 `SKILL.md` §4.1 反合理化红线）。

**适用范围（避免与重构冲突）**：红→绿硬门针对**改变行为的**代码（新功能、修 bug）。**行为保持型重构**走等价路径：先确认基线测试全绿 → 每步变换后立刻重跑基线保持绿 → 全套对比基线输出；重构本来就是"红→绿→重构"循环里在绿灯下做的那一步，不要求先造一条人为失败的测试。但**任何**代码改动（含重构与小修）都仍须落 VERIFY-LOG 证据才能过 G3——TDD 红灯可豁免，验证证据不可豁免。

1. **红灯**：先写一条能复现问题/表达需求的测试，**跑它、看到它真的失败**（证明测试有效）。记下失败测试指针（文件/用例）+ 红灯输出摘要。
2. **进阶**：写让它通过的最小实现——没有红灯记录就不许写实现。
3. **绿灯**：跑测试转绿，记绿灯输出摘要。
4. **重构**，保持绿；重构后重跑。

记账格式（落 `.project_memory/tmp/VERIFY-LOG.md`，与验证台账共用一份）：

```
- 2026-11-26 · TDD 红灯 · <失败测试指针> :: <红灯输出摘要>
- 2026-11-26 · TDD 绿灯 · <命令> :: <绿灯输出摘要>
```

G3 核验"红灯记录存在"才放行；缺红灯视为未过 G3（无兼容：没记 = 没做，不因"其实测过了"放行）。

## 3. 测试质量
- 测行为不测实现；断言具体输出/状态，不断言调用细节。
- 测试名说明"什么条件下应该怎样"。
- **绝不弱化/跳过/删测试、不 mock 掉被测对象**。mock 只用于隔离外部依赖（网络/时间/数据库），不用于让失败变绿。
- 每个新检查要自证有效：重新引入真实旧错误 → 跑 → 失败 → 移除 → 通过。

## 4. 固件与数据
- 测试数据最小化、自包含；不依赖执行顺序与外部环境。
- 固件（fixture）复用有度，避免"改一个固件坏一片测试"。

## 5. 覆盖率
覆盖率是发现未测路径的工具，不是目标数字；重点覆盖新增逻辑与关键路径，不追求虚高。
