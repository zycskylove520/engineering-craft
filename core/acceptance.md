# 用户验收

> 适用：交付前，让"做完了"由使用方/需求方确认，而不是 agent 自说自话。与 `core/requirements.md` 互补：那里定**开工前**的验收标准（G1 门），这里做**交付前**的验收执行。来源：2026-11-23 补验收缺口。
>
> **按需**：小改动可裁剪到"对照 PRD 验收标准跑一遍 + 贴输出"；涉及用户可直接感知的行为变化、多模块联动、上线发布时，走完整流程。

## 1. 对照验收标准逐条核

- 取 `core/requirements.md` 的 PRD 验收标准（Given-When-Then 或"输入→动作→预期输出"）逐条执行，**一条一条贴真实输出**，不合并成一句"都通过了"。
- 每条标结论：通过 / 失败 / 无法验证（说明缺什么环境或数据）；**失败或无法验证的不算完成**。
- 边界与异常路径至少各覆盖一条；只测正常路径的验收不成立。

## 2. 谁验

- 需求方/用户在场 → 请他按自己的场景试用一轮，观察是否与预期一致；记录他提出的偏差，视为新需求走需求循环，不在交付前硬塞。
- 用户不在场 → agent 按验收标准自验，但结论必须标"自验，待用户确认"，不冒充用户验收；交付说明里列清"哪些需要用户亲自确认"。

## 3. 偏差处理

- 验收不通过 → 回退到对应阶段修（功能不符回编码，环境问题回配置），修完重跑该条验收，**不弱化验收标准来让它通过**（同 `core/testing-strategy.md` 不弱化测试的纪律）。
- 验收中发现的新诉求 → 记为新需求，走下一轮需求循环（见 SKILL.md 第六节），不扩大本次范围。

## 4. 交付证据

- 验收记录写成可审文本（`.project_memory/tmp/` 临时产物或交付说明附件），含：验收标准条目 / 执行命令或操作步骤 / 真实输出 / 结论 / 谁验的。
- 交付说明引用该记录；证据分级照旧（实测/推断/猜测），未跑的条目不许写"通过"。

## 5. 完成检查

- [ ] PRD 每条验收标准都有真实输出与结论，边界/异常路径各覆盖一条？
- [ ] 用户不在场时标了"自验待确认"，未冒充用户验收？
- [ ] 失败项回退修复并重验，未弱化标准；新诉求转下一轮需求循环？
