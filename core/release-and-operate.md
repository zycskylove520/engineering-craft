# 发布与上线后运维

> 适用：合并之后到"真正跑起来且稳定"之间的一段——发布交接、部署、回滚、上线后观察、事件响应。来源：2026-11-23 补运维缺口，对标 Agentic SDLC 的 Release / Operate 阶段与 devOpsGPT 的部署测试。
>
> **边界（能力诚实）**：发布与运维在成熟框架里被标为 `Emerging` / `Directional`——agent 能起草 changelog、关联告警、写事件时间线，但**不能对生产变更做 go/no-go，也不能独立处置故障**。本文件的动作默认**人类主导、agent 辅助**；没有 CI/CD、监控、runbook 等平台能力时，按 P0 铁律第 8 条如实降级说明，不假装自动化。

## 1. 发布交接物（合并门之后、部署之前必须齐）

交付（`core/delivery.md`）到合并门为止；发布另需三样，缺一不发：

- **发布清单**：本次版本包含哪些改动（对应 PR/提交）、面向用户变了什么、影响范围与破坏性变更（breaking change）。
- **回滚预案**：怎么退回上一版（具体命令/版本号/数据迁移是否可逆）、回滚的触发条件、回滚后需要验证什么。
- **观察项**：上线后盯哪些信号（错误率/延迟/关键业务指标/日志异常）、正常基线是多少、观察多久。

三样写成可审文本（工程记忆或发布说明），不写在聊天里——换上下文仍可查、可审计（同 `core/operations.md` 状态写文件原则）。

## 2. 部署前检查门（全真才发）

- [ ] 合并门全绿（继承 `core/delivery.md` 第 4 节），产物是已验证的那份（版本/hash 对得上）。
- [ ] 配置/环境变量/密钥按环境区分，敏感信息不硬编码（P0 第 6 条）；密钥由人注入，不进仓库、不进日志。
- [ ] 数据库/数据迁移：方向、兼容性、可逆性已确认；不可逆迁移需人明确拍板。
- [ ] 破坏性变更已通知下游/调用方；版本号与变更日志已更新。
- [ ] 回滚预案可执行（命令在目标环境验证过或至少有明确出处），不是空话。

任一不满足 → **不发**，列出缺口交人决定。go/no-go 是人的决定（Agentic SDLC 的 Human Layer）。

## 3. 上线观察

- 按发布清单的观察项盯基线；异常先对照回滚触发条件，不现场拍脑袋改生产。
- 区分"部署引入的"与"本来就有的"：用上线时间点前后对比，需要时关联最近部署记录（agent 可做关联辅助，判断归人）。
- 观察结论记回发布记录：正常/异常、证据（指标/日志/命令输出）、是否触发回滚。

## 4. 事件响应（人类主导）

- 人拥有事件指挥与可靠性决策；agent 只辅助：关联告警、起草时间线、检索 runbook、建议（非执行）回滚动作。
- 先恢复服务再查根因；每一步操作与证据按 `core/operations.md` 的 Ledger 记（时间/阶段/决定/原因/证据/结果），旧行不改只追加。
- 事后复盘按 `core/retrospective.md`：教训升级到对应规范层，不留在聊天里。

## 5. 与相邻规范的关系

- `core/delivery.md`：管到 PR/合并门；本文件从合并门接着往后管。
- `core/operations.md`：管"长任务上下文接力"，不是部署运维；两者都遵循"状态写文件"。
- `core/verification.md`：发布前的验证纪律在此复用，不重复定义。

## 6. 完成检查

- [ ] 发布清单 / 回滚预案 / 观察项三样齐，且写成可审文本？
- [ ] 部署前检查门全真；go/no-go 由人拍板，未越权自动发布？
- [ ] 上线观察有前后对比证据；异常处置按 Ledger 留痕？
- [ ] 平台能力不足处如实降级说明，未宣称自动化运维？
