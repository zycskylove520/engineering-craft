# 评审与自审

> 适用：交付前自审、评审他人改动、看 findings。来源：原 8.6。

## 1. 圈范围
- `git status --short` 圈范围，不 stash/discard/带入无关文件。
- `git merge-base` 定基线，同一 diff 命令看到底。
- **没通过检查的改动不送审**。

## 2. Brief（给评审视角）
写清：仓库 / 基线 / diff 命令 / 目标一句 / 范围外 / 检查结果。
评审者只看不改、不提交、不推送；读 diff 周围代码，找 bug、坏掉的调用方、与目标不符的缺口；标记目标不需要的代码；风格问题除非掩盖 bug 否则忽略。
（无子代理时用新上下文或逐条自审代替，效果打折。）

## 3. Findings 结构
写成：`id 严重度 文件:行 问题 修法`；严重度 = **blocker**（目标用例就是错的）/ **should**（真 bug）/ **nit**。首行给 `VERDICT: APPROVE | CHANGES`。

## 4. 逐条自判
- 同意 → 做最小修复（优先删/收窄）。
- 不同意 → 带 `文件:行 + 输出` 反驳。
- nit / 范围外 → 一句拒绝。
- **4 轮封顶**，只剩 nit 或 APPROVE 就停；争议两次请用户定。diff 变大就削回。

## 4.5 APPROVE 附带项的收口责任（2026-11-23 实测补充）

**FINDINGS 的落点（先定，避免悬空）**：就是 §3 评审产出的交接物文件 `FINDINGS.md`（工作区临时产物，与 `BRIEF.md` 同目录），结构为 findings 表（`id/严重度/文件:行/问题/修法/状态`）。lead 收尾补记时在该 finding 行追加"验证命令 + 真实输出摘要 + 日期 + 状态=已修复已复验"；不另起第二个台账。若某任务未产出 `FINDINGS.md`（单人自审裁剪），补记进交付说明的"已知限制/已修项"即可。

评审给的 `should`/`nit` 不阻断 APPROVE，但**不能就此悬空**——每条都要有明确归属与状态，否则交付时用户不知道它是修了还是留着：

- **should（真 bug，但不破坏目标用例）**：lead 判断——属本次可安全收尾的小修（改动局部、证据可复验）→ lead 在 APPROVE 后自己收尾并**跑回归验证、把结果补记进 FINDINGS**；涉及大改或需要上游重审 → 退回对应岗位，不塞进 lead 收尾。
- **nit（风格/文档/死资源）**：修就修、不修就明确写进交付说明的"已知限制"，二选一，不许沉默。
- 实测：go-no-go 响应展开路径串（should）由 lead 收尾修复并补记；locale 死资源（nit）先列限制、后由用户要求才补做——两种处理都成立，关键是**状态可见**。

## 4.6 lead 收尾的硬约束

lead 收尾修复必须：① 只改评审点名的局部；② 重跑窄检+全套，条目级复验该 finding；③ 在 FINDINGS/交付说明留痕（含真实输出）。**不允许以"评审已过"为由跳过验证**，收尾改动同样要过 `core/verification.md`。

## 5. 多方案择优（N=3–5）
各在独立输出目录、互不可见，共享一张 3–6 条可查评分表；先 build/test 淘汰跑不起来的，按结构而非抛光选基准，只嫁接别家具体强项（一条测试/一个边界/一个更净的函数），不合整文件，重跑全套。
