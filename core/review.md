# 评审与自审

> 适用：交付前自审、评审他人改动、看 findings。来源：原 8.6。

## 1. 圈范围
- `git status --short` 圈范围，不 stash/discard/带入无关文件。
- `git merge-base` 定基线，同一 diff 命令看到底。
- **没通过检查的改动不送审**。

## 2. Brief（给评审视角）
写清：仓库 / 基线 / diff 命令 / 目标一句 / 范围外 / 检查结果。
评审者只看不改、不提交、不推送；读 diff 周围代码，找 bug、坏掉的调用方、与目标不符的缺口；标记目标不需要的代码；风格问题除非掩盖 bug 否则忽略。
（无子代理时用新上下文或逐条自审代替，效果打折。）

## 3. Findings 结构
写成：`id 严重度 文件:行 问题 修法`；严重度 = **blocker**（目标用例就是错的）/ **should**（真 bug）/ **nit**。首行给 `VERDICT: APPROVE | CHANGES`。

## 4. 逐条自判
- 同意 → 做最小修复（优先删/收窄）。
- 不同意 → 带 `文件:行 + 输出` 反驳。
- nit / 范围外 → 一句拒绝。
- **4 轮封顶**，只剩 nit 或 APPROVE 就停；争议两次请用户定。diff 变大就削回。

## 5. 多方案择优（N=3–5）
各在独立输出目录、互不可见，共享一张 3–6 条可查评分表；先 build/test 淘汰跑不起来的，按结构而非抛光选基准，只嫁接别家具体强项（一条测试/一个边界/一个更净的函数），不合整文件，重跑全套。
