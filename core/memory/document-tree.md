# 目录组织 · 逻辑文档树怎么划

> 能力：定义"记忆文档怎么分、怎么嵌套、怎么被找到"。与"单条记忆长什么样"（`content-model.md`）正交。
> 本文件是 `core/memory/` 能力簇之一；簇索引见 `core/project-memory.md`。
> 本 skill 是宿主无关的通用规范：工程记忆就是项目里 `.project_memory/` 下的普通 Markdown 文件，**用什么工具读写由宿主决定，本 skill 只管文件该长什么样**。

## 1. 划分原则：顶层按职责切目录，目录内按子系统分文件

记忆目录是**两个正交维度**：

- **顶层目录 = 职责**（单一职能原则）：架构、写法规范、测试、构建……每个目录只装一类职责，不混。禁止把所有内容堆进一个 `modules/` 大杂烩。
- **目录内文件 = 子系统/主题**（数量动态）：每个职责目录里，按源码真实子系统或主题分文件，有几个子系统就几个文件，不设上限、不预设模板。

默认标准结构（**6 个核心职责目录 + 3 个根文件，全部建**，每个目录内文件数量动态）：

```
.project_memory/
├── INDEX.md                    短导航（唯一强制全读，必须短）
├── status.md                   项目当前状况快照（现状/进展/健康度，见 §5）
├── open-questions.md           未决 / 技术债 / 框架问题清单（见 §6）
├── tmp/                        执行临时产物区（PLAN/PROGRESS/… 见 §7，不进规范层）
├── architecture/               【职责：为什么这样设计】骨架/边界/耦合/关键决策
│   ├── overview.md              整体架构
│   ├── <子系统A>.md             每个一级子系统单独成篇（数量动态）
│   └── <子系统B>.md
├── conventions/                【职责：应该怎么写】写法规范/配方
│   ├── naming.md                通用命名/分层/错误处理
│   └── <子系统或主题>.md         每个子系统/高频主题单独成篇（数量动态）
├── api-contracts/              【职责：对外怎么被调用】公开 API / CLI / 配置格式 / 数据协议
├── data-model/                 【职责：数据长什么样】schema / 数据格式 / 状态结构 / 领域模型
├── testing/                    【职责：怎么测】测试固件 / mock 边界 / 覆盖率约定
└── build/                      【职责：怎么构建】依项目构建方式分文件，如
                                build/cmake.md、build/cargo.md、build/pnpm-workspace.md、
                                build/setuptools.md、build/maven.md（按项目实际，文件动态）
```

**为何 6 个都核心**：职责是稳定的"关心角度"，与项目类型无关——再小的项目也有对外接口、数据形状、构建方式、测试方法，只是内容多少不同。全建保证跨项目结构一致、可比；内容可以薄，但不能缺位。空目录不留内容占位，INDEX 里指向"暂无"即可。

**为何 `build/` 独立且不并入 `architecture/`**：构建方式因项目而异（CMake / Cargo / pnpm workspace / setuptools / Maven…），各有自己的语义；并入 architecture 无法适配所有项目。用短名 `build/`，目录内按实际构建方式分文件——既不掺"架构"语义，又能容纳任意构建体系。

**标准目录集之外**：确有标准集覆盖不了的职责，允许增补目录，但必须在 `INDEX.md` 登记一行并写明理由——项目记忆要跨项目可比，不能像 skill 自身文件那样纯靠"列目录发现"。正文只定义这 6 个标准职责目录。

**职责目录判定**：目录名就是职责边界——`architecture/` 只放"为什么这样设计"（DECISION 为主），`conventions/` 只放"应该怎么写"（RULE 配方为主），两者不混。一个子系统在多个职责目录里可以各有自己的文件（如 `architecture/engine.md` 讲引擎为什么这样设计，`conventions/engine.md` 讲新增引擎怎么写）——**按职责分目录，不按子系统分目录**。

**两步定位测试**：agent 写某子系统代码时，能否两步内定位到所有该遵守的规范（对应职责目录下的子系统文件 + 通用文件）？不能就是组织得不好，规划阶段打回重排。

## 2. 组织纪律

- **单一职能目录**：每个顶层职责目录只装一类职责；新增职责就新增目录，不往已有目录塞异类内容。
- **目录内按子系统分篇**：源码每个一级子系统在自己的职责目录里都有对应文件；子系统内部再按职责细分。禁止多个子系统挤进一个文件。
- **一段一关注点**：单个段落只讲一件事。发现一段混了三件事（如"注册装饰器 + 检测头双模式 + CSP 命名"）就拆段或拆篇。"一篇一关注点"在段落级同样成立。
- **能套用的规则写成"配方"**：新增 X 该抄哪个文件、改哪几处、按什么顺序——见 `content-model.md` §3。
- **嵌套不限深度**：按项目复杂度决定，不套固定模板，也不为省事压平。
- **每篇开头写边界声明**（见 `content-model.md` §4）。
- **INDEX 必须短**：每篇一行指针 + 一句"这篇管什么"，不放内容。落盘后必须更新 INDEX。
- **日常收敛**：追加规范优先并入已有文件，避免碎片化；"多建"是建库期原则，不是日常纪律。

## 3. 必挖清单（通读阶段覆盖度判据）

通读源码时逐项挖，缺项不进规划：

1. **构建系统**：入口、依赖图、模块边界、耦合方向、脚本任务——**当架构读，不当配置抄**。
2. **目录职责**：每个顶层目录"为什么在这"，逐个自悟，不按目录名推断。
3. **功能模块**：入口 → 核心逻辑 → 数据流 → 错误处理 → 测试方式 → 对外契约。
4. **横切约定**：命名、分层、依赖注入、错误处理、日志、配置、测试固件。
5. **例外与反例**：不一致处（技术债或有意设计）→ `open-questions.md`。
6. **配方候选**：对"新增任务/模块/模型/后端"这类高频动作，边读边记"完整走一遍要动哪些文件"——最有价值的套用规则，优先沉淀。

产出结构由 agent 按证据决定——这份清单是覆盖度下限，不是模板。

## 4. 落盘方式（宿主无关）

工程记忆是项目里的普通 `.md` 文件树，按 §1 的目录组织直接建目录、写文件。宿主提供什么读写手段是宿主的事，本 skill 不假设任何特定工具、接口或固定文件名集合。

**安全纪律（与工具无关，始终成立）**：所有写入路径必须落在项目根的工程记忆目录内，不越界；每条规范带来源与日期（见 `content-model.md`）。

**内容禁止项（项目记忆必须自包含、可迁移）**：
- **不得写入任何本机绝对路径**——尤其是本 skill 的安装路径、agent 运行环境路径（如 `C:/Users/.../.dsh/skills/...`）。项目记忆会随项目走、换机器/换 skill 位置就失效；要引用流程，写动作本身（如"写码前按检索套用流程：读 INDEX → 定位文档 → 取条目 id"），不指向 skill 文件。
- **证据路径一律用项目内相对路径**（相对项目根），不用绝对路径。
- 一句话判据：把这份记忆拷到另一台机器、另一个 agent，里面的路径和流程指引还成立吗？不成立就是写了不该写的外部路径。

## 5. status.md · 项目当前状况快照

一份展示"项目当前是什么状态"的文档，属长期记忆目录（与 INDEX 并列）。内容：

- **当前阶段**：项目处在什么状态（原型 / 开发中 / 稳定 / 重构中 / 待发布）。
- **已完成 / 进行中 / 规划中**：当前有哪些模块做完、哪些在做、哪些待办。
- **健康度**：测试覆盖、已知阻塞、技术债总量（可指向 `open-questions.md` 计数）。
- **最近变更**：最近几次**项目本身的**重要变更（新模块落地、架构调整、版本发布等）的日期 + 一句话，滚动更新、限定最近若干条。
- **不写一次性排查插曲**：调试过程、临时现象（如"git 显示 M 实为 CRLF/LF 行尾差异"）属一次性流水，不是项目状况——这类内容放 `tmp/` 或不留，**不进 status**。
- **何时更新**：每次交付后刷新；它反映的是"此刻状况"，不是历史档案，也不是工作日志。

与 `open-questions.md` 分工：status 是**全局状况快照**（含健康度概览），open-questions 是**问题明细清单**；status 引用 open-questions 的增长/收敛趋势，不重复列出每条问题。

## 6. open-questions.md · 框架问题清单（属记忆目录，随修复递减）

未决问题、技术债、疑似 bug、半成品/死代码——**属于项目记忆目录**，作用是让用户一眼看清"当前框架哪里有问题"。

- **随修复递减**：问题被修复后，从活跃清单移除（或标记已解决并归入"已解决"小节按不遗忘原则保留痕迹），总数应随项目推进逐步减少——这是项目健康度的晴雨表。
- **等级与状态分列**：每条标证据路径 + 日期 + 事实等级（只用 `content-model.md` §5 的实测/推断/用户约定一套）+ 核实状态（已复核/待复核）。两者是正交字段，**不许把状态塞进等级**（禁止"推断（子代理报告，待复核）"这类混合写法）。未复核的观察标"状态: 待复核"，不写成定论。
- **需要人拍板的单列**：末尾设"待协商"小节，明确哪些问题需要用户决策（修不修、优先级、是否提取公共基类等）。
- **与规范层的关系**：问题修复后形成的长期约定写回对应职责目录（architecture/conventions），open-questions 里标已解决——不把已确认的规范留在问题清单里。
- **不放执行流水**：它是"问题清单"，不是任务执行日志；执行产物（PLAN.md / PROGRESS.md 等）统一放 `.project_memory/tmp/`（见 §7），不进规范层。

## 7. tmp/ · 执行临时产物区（不污染项目空间）

`.project_memory/tmp/` 是项目记忆目录内的**临时区**，专门收纳任务执行产物，避免在项目根散落文件：PLAN.md、PROGRESS.md、GATE-LOG.md、FINDINGS.md、BRIEF.md、notes/、验收记录、联调记录等一律放这里。

- **不是职责目录**：tmp/ 不属于 6 个标准职责目录，不参与"按职责分目录"的结构；它是记忆目录内的例外区。
- **不进规范层**：里面的内容是流水/草稿，不是长期规范；只有经确认的长期约定才从 tmp/ 提炼进职责目录（提炼后 tmp 原件可清）。
- **可清理**：任务结束后 tmp/ 内容可删；它不是记忆的长期组成部分。
- **INDEX 不登记**：tmp/ 不进 INDEX 指针（INDEX 只导航规范层）。
- **落点纪律**：所有执行产物必须写进 tmp/，**不得散落在项目根或其他目录**——这是"不污染项目空间"的硬要求。

## 8. 与其他能力的关系

- 单条陈述怎么写（kind / 证据 / 配方 / 边界声明）→ `content-model.md`。
- 通读→规划→落盘→自检的操作顺序 → `workflows/init-project-memory.md`（本文件的必挖清单被它引用）。
- 写码时怎么检索这套结构 → `retrieval-and-writeback.md`。
