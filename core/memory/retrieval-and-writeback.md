# 使用闭环 · 写码时检索套用，新模式验证后回灌

> 能力：让工程记忆"能被用起来"——agent 首次通读整理后，后续写业务/核心代码时能自主套用已有写法；套用中产生的新模式能被沉淀。
> 本文件是 `core/memory/` 能力簇之一；簇索引见 `core/project-memory.md`。
> 目标判据：agent 写新代码时，是否真的按项目已有的写法写——不是"泛泛风格一致"，是"像这个项目的人写的"。

## 1. 检索套用（写码前 · 机械动作）

在任何写核心代码的工作流里执行，不可省略——`workflows/feature.md`（编码实现步前）、`workflows/bugfix.md`（定位阶段）、`workflows/refactor.md`（改前）。`workflows/investigate.md` 不直接写码（转 bugfix），无需单独执行：

1. **列出检索线索**：本次要改的模块名 + 涉及的横切关注（命名/分层/DI/错误处理/异步/日志/测试）。
2. **按线索定位记忆（匹配策略）**：先读短 INDEX 找到相关规范单元路径，再打开对应文档取 `RULE`/`FACT`/`DECISION` 条目。检索按以下顺序，命中即停：
   1. **字面整句优先**：用完整线索串（模块名 + 关注点）做精确匹配；
   2. **零命中分词回退**：拆成关键词、再退到二元组（相邻两词）匹配；
   3. **相关性排序**：多命中时按相关度排序、只取最相关的若干条，不倾倒全目录；
   4. 可用 kind / 层（目录）过滤缩小范围。
   用什么手段定位由宿主决定，本 skill 只要求"按此策略命中相关条目"。
3. **列进 PLAN.md**：把命中的规范条目编号（或其锚点）列进 `.project_memory/tmp/PLAN.md`（临时产物，不进规范层），作为本次编码必须遵守的约束清单。条目须带 id/kind——正文命中时也要返回整条（含 header 的 id/kind），否则无法列入约束。
4. **编码时逐条对照**：每写一处关键代码，回看约束清单——命名、结构、依赖注入、错误处理、测试方式照已有写法来；有配方式规则的直接按编号步骤走。
5. **无命中时如实说**：定位不到相关规范，就在 PLAN.md 标"无既有约定"，不凭空编一条规范充数。空线索不检索正文（否则返回无关噪声），只列带 id 的条目。

> 记忆记得再全，写码时不检索也是白搭。这一步是把"记忆"变成"行为"的唯一接口。

**写进 INDEX 时只写动作、不引 skill 文件**：INDEX 里说明"怎么定位记忆"时，直接写动作序列（读 INDEX → 按线索定位文档 → 取条目 id → 无命中标"无既有约定"），**不要写"先读 `<skill 安装路径>/core/memory/retrieval-and-writeback.md`"这类指向本 skill 文件的绝对路径**——项目记忆要自包含、可迁移，换机器/换 skill 位置后绝对路径会失效（见 `document-tree.md` §4 内容禁止项）。

**条目锚点**：每条可套用规则带一个稳定短 id（如 `R-ENG-01`、`R-DATA-03`），编号同一文档内不复用。INDEX 与 PLAN.md 用这个 id 指代条目——代码和文档都在变，靠 id 而非行号/标题定位才稳。这个 id 已包含在 `content-model.md` 的五件套里（五件套 = 稳定 id + kind + 陈述 + 证据 + 日期与事实等级），不是额外附加项。

## 2. 模式回灌（验证后 · 条件动作）

写码过程中产生**新的可套用模式**（项目此前没有、且被真实验证有效的写法）时：

1. **先验证**：新模式必须跑过真实检查、贴出输出（P0 第 2 条）——没验证的写法不回灌。
2. **再判断**：是"一次性解法"还是"可复用约定"？只有后者回灌；前者留在代码里，不进记忆。
3. **按格式写回**：用 `content-model.md` 的五件套（稳定 id + kind + 陈述 + 证据 + 日期与事实等级），优先并入已有文档（`document-tree.md` §2 日常收敛）。
4. **更新 INDEX** 若新增了文档。
5. **用户约定优先**：涉及架构/规范变更的回灌，按阶段门由人确认（G2），agent 不擅自把个人偏好升格为规范。

## 3. 多 agent 场景下的套用

- 并行开发的每个单元，**各自**执行 §1 检索套用——不能因为 lead 读过记忆就跳过。
- lead 集成时对照各单元的 PLAN.md 约束清单核一遍：写法是否与记忆一致、是否有单元自创写法而未回灌。
- 验收时把"是否套用已有规范"加入本次核对项（这是一条新检查要求，不是 `core/integration.md` 现有清单里的条目）。

## 4. 自检关联

建库阶段自检清单有一条"闭环可用：写码前能检索到规范"（见 `workflows/init-project-memory.md` 步 4 自检），它验证的只是"检索可达"。本文件定义的检索套用与模式回灌，是让这条闭环真正转动的执行细则。

## 5. 与其他能力的关系

- 检索到的条目长什么样、怎么判断是不是 RULE → `content-model.md`。
- 检索线索里的"模块名 / 分类"从哪来 → `document-tree.md` 的分类。
- 写码前必读语言规范的硬规则在 `SKILL.md` P0 第 1 条——本文件的检索是**补充**，不替代语言规范。
