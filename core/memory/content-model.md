# 内容模型 · 一条工程记忆长什么样

> 能力：定义"什么算一条合格的记忆"。这是写记忆时的判据，与"怎么组织文档"（`document-tree.md`）、"怎么建库"（`workflows/init-project-memory.md`）正交。
> 本文件是 `core/memory/` 能力簇之一；簇索引见 `core/project-memory.md`。

## 1. 四种陈述类型（kind）

每条记忆陈述必须归入且仅归入一种：

| kind | 含义 | 例 |
|---|---|---|
| `RULE` | 应该怎么做（长期约定、可套用的写法） | service 依赖统一构造函数注入，不在方法内 new |
| `FACT` | 项目是什么（技术栈/依赖/定位，客观） | 状态管理用 Zustand，slice 按业务域切 |
| `DECISION` | 为什么这么选（取舍、背景） | 选 pnpm workspace 而非 monorepo 工具，因为构建链简单 |
| `OPEN` | 未决/待协商/技术债/不一致处 | 两处 letterbox 实现重复，待定夺归并方案 |

一篇文档可含多种 kind 的陈述，但**一个关注点一篇**（见 `document-tree.md`）。

## 2. 每条陈述的五件套（缺一不落盘）

```
- [RULE R-SVC-01] service 层依赖一律通过构造函数注入，不在方法内 new。
  证据: src/order/order.service.ts, src/user/user.service.ts
  记录: 2026-11-24 · 实测
```

1. **稳定 id**——短标识（如 `R-SVC-01`），同一文档内不复用；供 INDEX、PLAN.md、后续代码评审精确指代（见 `retrieval-and-writeback.md` 条目锚点）。
2. **陈述正文**——写成"可套用的模式"，不是"项目描述"。
3. **kind**——四选一，标在方括号里，跟在 id 前。
4. **证据**——文件路径或用户明确约定，指向"在哪能找到这个模式"（§3 证据不绑死瞬时行号）。**没有证据就不写这条**——这是 skill 自己的纪律（P0 第 4 条），不假设宿主工具会替我们拦。
5. **日期 + 事实等级**——`YYYY-MM-DD · 实测/推断/用户约定`。没有证据支撑的猜想标"推断"，不许写成"实测"。

## 3. 第一公理：写规则，不写清单；能套用的写成配方

**判断法**：陈述里出现具体计数（"16 个 service"）、可枚举清单（"a/b/c 三个模块"）或会随时间变化的 roster → 一律改写成规律。

| 反例（清单，会过期） | 正例（规则，可套用） |
|---|---|
| "项目有 16 个 service" | "service 统一一条业务一个文件、类名 `<域>Service`、依赖构造函数注入" |
| "有 auth / order / user 三个中间件" | "中间件按横切关注切成独立文件、在入口按序注册" |
| "用了 Redis 和 RabbitMQ" | "跨进程缓存走 Redis、异步事件走消息中间件，配置集中在 config/" |

理由：清单下个月就错；规则才长期有效，而且**规则才能派生代码**——这正是"agent 读完后能按已有写法写新代码"的目标所在。

**配方优先**：描述式规则（"现状是这样"）只占少数；高频动作（新增任务 / 模块 / 模型版本 / 后端 / 测试）必须有**配方式规则**——编号列出"抄哪个文件 → 改哪几处 → 按什么顺序 → 怎么验证"。判断标准：读完这条，agent 能否直接动手而不必再回头翻源码找参照？不能就不是好配方。自检时检查配方式规则的覆盖面（见 `workflows/init-project-memory.md` 完成检查）。

**证据指向模式，不指向瞬时行号（硬要求）**：证据的**主体必须是文件路径 + 模式描述**（"在 `config_manager.py` 的 link 解析流水线里"），**行号只能作括号内的辅助**（`:65-124`），且不得作为定位的唯一手段——代码一改行号就失效，文件与模式描述才持久。

判断法：把这条证据里的行号全删掉，agent 还能按文件路径 + 描述找到这个模式吗？不能就是过度依赖行号，要补上模式描述。反例："证据: `config.py:65-124`"；正例："证据: `cfg/config_manager.py`（link 解析：校验路径→后缀分派→逐键 setattr；当时位于 :65-124）"。配方步骤里引用"参照 X 文件第 N 行"同理——先写清参照什么，行号作辅助。

## 4. 边界声明（每篇开头）

每篇文档开头用一句话写清"这篇管什么、不管什么"：

> 本篇管订单域 service 的写法与依赖注入方式；不管 controller 路由与数据库迁移。

自由文档结构下，边界声明替代旧固定层名（architecture/conventions/...）的职责说明，防内容漂移。

## 5. 事实等级纪律

- **实测**：亲眼在源码里读到、带路径证据。
- **推断**：从多个证据归纳出的模式，标明"归纳自 N 处"。
- **用户约定**：用户明确拍板的约定，标"用户约定 + 日期"。
- 不编造：读不到的接口、库、规范不写进记忆；宁缺毋滥。
- **等级只用一套**：工程记忆内部统一用上面三种，不另立"已核实/子代理报告/待复核"等等级口径。**事实等级（实测/推断/用户约定）与核实状态（已复核/待复核）是两个正交字段，不许混写成一个**——反例：`推断（子代理报告，待复核）` 把状态塞进等级，是错的；正例：等级写 `推断`，另起一行写 `状态: 待复核`。
- 未复核的观察只能作为 OPEN 条目进 `open-questions.md`（见 `document-tree.md` §6），标"状态: 待复核"，**不得写成 RULE/FACT/DECISION 规范**。
- **与 skill 全局分级的关系**：P0 第 4 条的"实测/推断/猜测"是**所有工程断言**的通用分级；本节的"实测/推断/用户约定"是它在工程记忆里的落地——区别只在第三档：全局的"猜测"即本节的"用户约定之外的未证实内容"，按上一条它不进规范层（只进 open-questions），所以规范层实际只会留"实测/推断/用户约定"三种。两者是同一体系的作用域特化，不是两套口径。

## 6. 现状 vs 基线冲突的裁决规则

当"项目现状"与"skill 通用基线"（如 `languages/` 里的类型注解、docstring、测试覆盖）不一致时，规范必须明确裁决，不能让后续 agent 自己猜：

- **跟随现状**：项目已有稳定、一致、被验证的写法（哪怕与通用基线不同）→ 新代码跟随现状，不擅自"纠正"。
- **向基线靠拢**：项目写法不一致、或明显是缺陷/半成品（见 OPEN 裁决）→ 按通用基线写，并在规范里写明"例外原因 + 何时统一"。
- **悬而未决**：既非稳定一致、又非明确缺陷 → 标 OPEN 待用户拍板，不写成 RULE。

每条涉及冲突的规范都要带这条裁决结论，否则后续开发会在"照抄现状"还是"按好习惯写"之间反复摇摆。
