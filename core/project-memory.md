# 工程记忆目录（只存规范 · 不遗忘）

> 适用：「开始工程」时建立/读取项目记忆。这是本 skill 的原创内核。

## 1. 目录结构
```
<项目根>/.project_memory/                # 默认名（隐藏目录），冲突时 .project_memory_engineer/
├── .engineering-craft                  # 标记文件：由本 skill 创建 + 选定目录名
├── INDEX.md                            # 唯一强制全读的导航，必须短
├── architecture/                       # 【架构层】设计思想与决策（是什么+为什么）
│   ├── overview.md                     #   整体架构：分层/模块/调用链/数据流
│   └── decisions.md                    #   关键决策及理由、取舍
├── conventions/                        # 【规范层】编码约定
│   ├── naming.md                       #   命名规范
│   └── practices.md                    #   使用习惯、目录约定、格式/lint/测试约定
├── project.md                          # 【项目层】定位、技术栈、依赖约束
└── open-questions.md                   # 【待办层】未决问题、待重构的不合理设计
```

## 2. 各层职责
| 层 | 存什么 | 不存什么 |
|---|---|---|
| INDEX | 架构/规范地图、各文件指针 | 详细内容 |
| architecture | 设计思想、模块边界、关键决策与理由 | 某次改动过程 |
| conventions | 命名、习惯、目录约定、格式/lint/测试约定 | 临时任务、流水 |
| project | 技术栈、语言、依赖约束、项目定位 | 会话日志 |
| open-questions | 发现的不合理设计、待协商调整、未决问题 | 已解决且落规范的事项 |

## 3. 建库流程
1. 定位项目根 → 确定记忆目录（默认名/标记/冲突避让）。
2. 有代码 → 通读全部源码（大工程分批，目标彻底了解）→ 沉淀架构/命名/习惯/约定，每条带证据（文件路径）→ 主动指出不合理设计（附路径与依据）→ 与用户协商修复方案、影响面、优先级，征询后动手，不擅自大改。
3. 无代码 → 与用户商谈架构/语言/命名/目录/技术栈/测试约定，不凭空生成 → 落盘为契约。

## 4. 铁律：只存规范，不遗忘
- 只存"这个工程应该长什么样、为什么这样设计、大家怎么约定"，是长期契约。
- 不设 archive、不做过期清理、不删除旧决策；旧决策被取代标注日期与原因、保留原文，不静默删除。
- 不记录会话流水；追加不覆盖，改旧规范标日期，保持可审查。
- 每条规范带来源（文件路径或用户明确约定），"我觉得"不算。
- 靠 INDEX 按需检索，不大范围倾倒——这是读取策略，不是遗忘。
- **边界**：执行计划（PLAN.md）、进度交接（PROGRESS.md）是工作区临时产物，**不进本记忆目录**；`open-questions.md` 只放未决问题与待协商的不合理设计，不放执行任务清单。临时产物完成后只把其中形成的长期约定写回规范层。

## 5. 何时写回
- 首次建库 → 写全部规范层。
- 架构/规范新增或变更（用户确认）→ 写回对应层，标日期。
- 发现不合理设计 → 记 open-questions，协商修复后把最终约定移入规范层，待办标已解决（不删条目）。
- **门反复拦截同一类缺失 / 纪律屡次被绕过**（见 `core/gate-metrics.md` 的 GATE-LOG 回看）→ 视为规范缺陷信号，把"哪条门/哪条约定该改"的结论写回对应规范层、标日期与证据指针；原始流水不写。
- 日常需求不改变规范 → 不写。
